The heavy commands, every `npm run sim:*` and `node scripts/sim.ts`, `npm run capture`, `npm run e2e`, `npm run build:map` and the browser benches in `e2e/`, call `yieldToTests` in `scripts/runs.ts` first. It runs the command again as a copy in a session of its own at the lowest CPU priority, and pauses the copy with all it started while a test run goes on the machine, such as a review's `.nexus/check`. A copy at the lowest priority alone still slowed a whole `npm test` beside it 1.3 times, as the two share the machine below the scheduler. So the test run gets the whole machine and keeps its time limits. Each side says what it met. The test run names the heavy commands that pause for it as it starts and as it ends. The heavy command says when it pauses and resumes, and at its end how long it was paused. Its own time limits went on counting during a pause, so it says that a timeout in it may come from a pause and that it should run again. They share notes in the `first-game-runs` folder of the system's temporary folder, so this holds across checkouts on one machine. A heavy command alone runs as fast as before. A new heavy command calls `await yieldToTests()` first, or runs through `node scripts/yield.ts <command>`. A command that skips both, such as `node scripts/sim/slide.ts` or `npx playwright test`, neither yields nor pauses.

To show a new view, add a scenario file to `scripts/capture/scenarios/`. It default-exports `defineScenario({ name, title, run })`. `run` gets the Playwright `page` and `shot(name, title)`. The whole run becomes the clip.

CI runs `npm run capture` on every pull request and publishes to `pr-assets` only what a reviewer needs. It compares each screenshot with the same screenshot from the CI run of the base commit on the pull request's base branch, or from the newest run of that branch that still has its screenshots. A screenshot that differs in any pixel is changed: `shot` takes it in the map's still pose (`scripts/capture/still.ts`), so an unchanged view matches pixel for pixel, and any tolerance would also hide a changed digit. A scenario's own `page.screenshot` calls are not still. It publishes the changed screenshots with the scenario's `clip.gif`, every image of a scenario that the base lacks, and every image of each scenario you name. Unchanged screenshots stay out. Without a run of the base branch to compare with, every scenario is new. A view that shows a live game at a moment set by the wall clock differs on every run, so it is published every time. Locally, `capture:publish` compares with nothing unless you pass `--reference <dir>`, takes names with `--scenario <name>`, and reads open pull requests from the GitHub API with `GH_TOKEN`.

Every CI job that needs Chromium installs it through `.github/actions/chromium`, which restores the browser and the `.deb` files of its system packages from the cache, skips apt when the runner image already has every package, and has nine minutes of its own. A slower install fails in words that name it, and no test step loses time to it: each step that runs tests or benches has its own limit, the minutes it had when one limit held the whole job, and the job's limit is the sum. The install's notice says what it took.

CI captures in the shards the `capture-shards` matrix lists; each runs `--shard=<n>/<count>` with the count from the matrix itself (`strategy.job-total`), and the `capture` gate and `publish-media` read every `captures-*` artifact, so the matrix is the one place the count lives. The planner (`scripts/capture/shard.ts`) fills the shards by the CI seconds in `scripts/capture/scenario-seconds.json`, longest first. Each shard reports its seconds by scenario in a `capture seconds` annotation and in its job summary, which the API serves even where the log cannot be fetched, and `npm run capture:timings -- --run <id>` writes them back into the file. `scripts/capture/plan.test.ts` fails when a scenario has no time or when the heaviest planned shard holds more than `SHARD_BUDGET_SECONDS` (450) at the matrix's count: add a scenario with its time, and add a shard when the plan no longer fits.

To publish a whole scenario, add a line to the pull request description, such as `Publish scenarios: map, fog`, or `Publish scenarios: all`. The names are scenario names, the folder names under `captures/`, separated by commas or spaces. An unknown name fails the publish and lists the known ones. CI reads the description when `publish-media` runs, so after you edit it, re-run that job.

`pr-assets` holds one commit and no history. Each publish replaces it with a commit that holds the folders of open pull requests, the newest `playtest/stage-<n>/` folder, and the publishing branch's folder rebuilt from its captures. A branch without an open pull request loses its folder at the next publish. The folder's `README.md` names the head commit the images show, the run of the base branch they were compared with, the published images by scenario, and the screenshots left out. Markdown links point at `refs/heads/pr-assets/<branch>/<scenario>/<file>`, never at a commit, so they show the newest publish and work while the pull request is open.

The run summary holds the same Markdown. The full set, with the video and the trace, stays in the run's artifacts (`captures-<n>` and `capture-recordings-<n>`) for the repository's artifact retention, beside the Playwright report. If your machine cannot install Chromium, push the branch, wait for CI, and run `npm run capture:fetch`.
