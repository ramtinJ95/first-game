# Browser tests and frame measurements

A browser test or a capture scenario enters a game through `openGame(page, { query, power, pauses })` in `e2e/support.ts`, which opens `/?play=rome` and waits for the top bar. It adds `pauses=off` unless `pauses` is true, so a test that plays through a battle at speed sees it play out, and a test of the pauses says that it wants them. Only a test of the start screen opens `/` itself. Browser tests draw the test drawing, because a browser test checks behaviour and not the picture, and CI draws in software. `playwright.config.ts` stores `draw=test` in the page's local storage, and `?draw=test` does the same by hand. `TEST_DRAWING` in `src/render/draw-options.ts` lists what it leaves out: the paper grain, the moving swell, and antialiasing, and it draws at half resolution, so a page draws only when something changes and a frame costs a fifth of the full one in software. A page opened with `?draw=full` draws everything, as the game and `npm run capture` do, and the smoke test does so. A browser test waits for the state it needs, such as a day, a panel, or a text, and never for a fixed time or a count of days in a count of seconds. To know the day by which something happens, play the state forward with the rules in the test, as `firstDayWhen` in `e2e/fog-game.ts` does. `?frames` shows the frame interval and the time of each drawn frame, median and p95 over 5 s, and `node e2e/frame-bench.ts` prints that for each layer and switch (`hide=<layer>`, `swell=off`, `antialias=off`, `resolution=<n>`) after `npm run build`, at the zooms `--zooms widest,middle,closest` names (and `plateau-middle,plateau-closest` over the Persian plateau), and for another checkout's build with `--root <dir>`. A frame starts only once the GPU has finished the one before: `draw` places a WebGL2 fence after each frame and draws nothing while it has not signalled, so a slow GPU never queues frames and a click or a screenshot waits one frame at most. A held frame sends the GPU nothing, not even a render into a texture, and keeps every change for the next frame. It only lays the cities out again, which is CPU work, so a click picks what the screen will show (`FramePacer` in `src/render/frame-pacer.ts`). `?frames` takes the `waitForGpu` path and places no fence, so the frame bench cannot show a skip. The capture's clip takes a frame only once the map has drawn, and skips a frame it cannot take in 5 s, because a screenshot asked for while a page loads can wait out its whole timeout and hold up the scenario's own shots behind it.
